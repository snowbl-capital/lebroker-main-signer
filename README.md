# lebroker Main signer

Signs, on its user's own machine, the signature requests lebroker's hosted service asks of their **Main** wallets, and only those lebroker's allowlist accepts. Everything else is left for the user to sign or not in the browser.

lebroker's hosted service never holds a Main wallet's key (HOSTED_SERVICE.md, D2): what its delegated keys can't sign becomes a signature request, which the web app's banner shows and the user signs in their browser wallet. This program is the optional piece D1 left for later, automatic signing for Main, in a first, simple version:

- **Local.** It runs on the user's machine, with their keys in a folder there. The keys never leave it.
- **Allowlist only.** It signs exactly what the web app would let the browser wallet sign (D43), with the same rules, copied from lebroker (below). Nothing is signed blind.
- **Several wallets.** One process signs for every Main wallet whose key file is in the folder, each under its own session.

It is its own repository, published at github.com/snowbl-capital/lebroker-main-signer. It copies the code it shares with lebroker until that code lives in a shared package (below, "Kept in sync with lebroker").

## What it signs, and what it refuses

For each waiting request of each wallet, it reads the user's accounts again from the service, then runs the allowlist (`src/signableRequest`, lebroker's `apps/web/src/helpers/signableRequest`):

| Request                            | Signed only when                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A venue's setup or renewal on Main | Hyperliquid: lebroker's named agent (`lebroker valid_until …`), 180 days at most, on mainnet, on Arbitrum or the chain `MAIN_CHAIN_ID` names. Aster: lebroker's agent, perps only, never Spot, never withdrawals, 180 days at most, for this Main. Polymarket Perps: lebroker's proxy, a week at most. Lighter: Main's proof of its own account for its own account, a day at most; a key registration at lebroker's indexes, 200 to 252, only.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| A transfer from Main               | Hyperliquid's `sendAsset` of USDC between the spot balance and the main dex's perps, or Aster's Spot transfer of USDT, to one of the user's own **open sub-accounts** as the service lists them now, and only when **an entry of Main's address book signed by Main's own key names it** (below). Polymarket's hashed commands are refused: they can't be read before they're signed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| A withdrawal                       | Hyperliquid's `withdraw3` or Aster's withdrawal, to **Main's own address** only. One exception, which opens Main's Lighter from inside lebroker (lebroker's D56): Hyperliquid's `withdraw3` whose request names Lighter (`depositVenue`), on mainnet, of 6 USDC at least, to **Main's own Lighter intent address as this signer reads it itself from Lighter** just before it signs (`createIntentAddress`, for Arbitrum and the signing wallet's own address, 5 seconds at most, no redirect), never an address the request names alone. When that read fails, nothing is signed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| A payment for gas                  | Hyperliquid's `sendAsset` of USDC from Main's own balances, on mainnet, on Arbitrum or the chain `MAIN_CHAIN_ID` names, $20 at most, to **lebroker's gas reserve as pinned for the deployment `LEBROKER_URL` names** (`GAS_RESERVE_DEPLOYMENTS`, by its origin), never an address the request names alone. Only dev's is pinned for now: production, and any other deployment, a local stack's included, pin none, and nothing of this kind is signed there. The chain the gas is for is the service's word, shown in the summary only.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| A LaMarge move                     | Only what LaMarge's own SDK (`@lamarge/sdk`) checks, held to the deployment the request names, production's or dev's: a permit to that deployment's escrow, a payment into it, paid by **Main's own address**, whose deliveries come from it too, each to **Main's own address** (the signing wallet's, never one the request names) in the delivery venue's own token on its chain (`receiveToken`, `receiveChainId`, as LaMarge's `CHAINS` names them), every payment of a take on one chain, and the whole take for at least what it pays less 1.5 % (`MAX_TAKE_LOSS_BPS`), counted on its totals, each side at its own token's decimals, a take paid inside Aster or Lighter to the maker of the take the request carries and nobody else (`checkAsterTakeIntent`, `checkLighterTakeIntent`), by that deployment's Lighter key, a refund of Main's own payment from its escrow, a withdrawal back to Main, LaMarge's Aster agent under that deployment's name, LaMarge's Lighter key at that deployment's index on Main's own Lighter account as the request names it, Main's sign-in on that deployment's app. A LaMarge send to another account on the same venue (lebroker's D69) only to one of the user's own **open sub-accounts** as the service lists them now, and only when **an entry of Main's address book signed by Main's own key names it** (below), for exactly the amount the request names, as the SDK rebuilds and checks it (`checkSend`): on Polymarket, from the operation the request carries, whose hash must be the one signed; a Polymarket send without it is refused. |
| Main's account mode                | Hyperliquid's `userSetAbstraction` (lebroker's D66), on mainnet, on the chain `MAIN_CHAIN_ID` names or one lebroker signs on: for **Main's own address** only, never one of its Hyperliquid sub-accounts, and to `unifiedAccount` only, never portfolio margin or standard again, with a nonce no more than an hour past when the request was asked, by the request or by this signer's own clock, whichever is earlier. Its summary says it switches Main's Hyperliquid account to unified mode. Its kind, `account-mode`, is one lebroker doesn't ask yet (below).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

Each kind has its exact signing domain and types; anything else is refused: an unknown kind, venue, domain, type or field, a chain the kind doesn't name, a request for another account than Main, a destination that isn't one of the user's accounts (or, for a payment for gas, the reserve pinned for the deployment), an approval that lasts too long. Typed data is signed only on the chain the allowlist returns.

**What a payment into LaMarge's escrow pins.** The payer (Main), the escrow (the request's deployment's), and each payment's delivery: its recipient (Main), its token and chain (the delivery venue's own), all on one chain, and the take's total value, which brings back at least what the take pays less 1.5 %. One costly fill of a sweep passes when the whole take keeps its value, as lebroker's own limits and LaMarge's `min_out` hold the whole take. lebroker's executor refuses at plan, before anything is withdrawn, a take this floor would refuse, so a refusal here never strands a withdrawal on HyperEVM or Polygon.

**Open, not pinned yet.** A `PayTake`'s `hashlock` and maker `recipient` are free: whether a hashlock the service chose could get round the pins above depends on LaMarge's escrow contract, to be confirmed with LaMarge.

**What a LaMarge take paid inside Aster or Lighter can't pin.** What Main signs for it is a transfer from Main's venue account to the take's maker: what it pays and to whom, never what comes back or where it goes. Those are in the take's fill (`amount_out`, `taker_recipient`, `delivery_to`), which the request carries as LaMarge's API answered lebroker, and which no maker signs. LaMarge's SDK holds that fill to Main as taker and receiver and to the take's minimum to receive, but on the service's word: unlike a payment into an escrow, these takes can't be held to Main's own address or the 1.5 % floor from what is signed. A compromised service could so drain Main's Aster or Lighter balance to a maker of its own: an open item, out of this signer for now.

A refused request is **never signed**. The signer logs `refused` with the allowlist's reason, once per request, tells lebroker with `POST /api/v1/signature-requests/<id>/decline` and that reason, and leaves it waiting for the user in the browser, where lebroker offers it at once and tells the user's channels. It checks it again on later passes, silently, in case the user's accounts change (a sub-account opening, for instance), and tells lebroker again each time its event stream opens again: lebroker keeps what it was told in memory only.

It also leaves alone what the user chose to put off (Later, a `deferred` request) and what has expired.

## Main's address book (lebroker's D70)

The accounts list is the service's word. A service gone wrong could list an address of its own as a sub-account and have Main's funds sent to it, so a transfer from Main to another account needs Main's own approval of that recipient too, which the service can't forge.

- **What it protects, and what it doesn't.** It protects against a service compromised _after_ the user approved their recipients: from then on, nothing the service adds to the accounts list is sent funds by this signer without a new signature of Main's. It doesn't protect against a service already compromised _when_ the user approves: the web app's prompt lists the addresses the service's accounts list gives, so a service lying then gets its address into the entry the user signs. The wallet shows each address in full; checking them is the user's part.
- **What the user signs.** In lebroker's web app (Settings, Address book, or the prompt on the Organization page and after a sub-account opens), the user signs in their wallet a plain-text message the wallet shows in clear (EIP-191). One entry names one address or several, every open sub-account in one signature:

  ```
  lebroker address book

  Deployment: <the app's host, such as lebroker.dev.lamarge.trade>
  Main: <Main's address, checksummed>

  I approve these addresses as recipients of transfers from this Main:
  - <label>: <address, checksummed>

  Date: <ISO 8601 time, UTC>
  ```

  "Remove", in Settings, signs the same message with `I withdraw approval of these addresses as recipients of transfers from this Main:` in place of the approval's line. For each address, the latest dated entry naming it holds; a withdrawal dated the same as an approval holds over it. An entry dated more than 10 minutes (`ADDRESS_BOOK_MAX_SKEW_MS`) past this machine's clock says nothing, approval or withdrawal, and is never written to the record: a far-future approval would otherwise hold over every withdrawal after it. Keep this machine's clock set.

- **What this signer checks.** Before each pass signs anything, it reads the address book (`GET /api/v1/address-book`) and keeps only the entries whose message reads as an entry word for word, names this wallet's own address as Main and `LEBROKER_URL`'s host as its deployment, and whose signature recovers to that address (`verifiedAddressBookEntry`, viem's `verifyMessage`). What an entry says is read from the signed message itself, never from the service's own fields. An entry signed on another deployment, dev's on production for instance, approves nothing here. The allowlist takes the recipients the latest entries approve (`approvedRecipients`). `ownSubAccount`, which every rule that sends from Main to another account passes through, refuses an open sub-account no such entry approves: `This request sends funds to an account your address book doesn't approve: …`. The request is declined and left to the browser, as every refusal is.
- **What it remembers.** Every entry it checked is also written to a file on this machine (`MAIN_ADDRESS_BOOK_FILE`, `address-book.json` in the key folder by default): each entry's message and signature, addresses only, no key, read back and checked again at the start. The service's list adds to it and never takes from it, so a withdrawal this signer has seen holds though the service later stops listing it and replays the older approval. A file this signer didn't write stops the start; one it can't write is logged (`failed`, step `record`) and tried again on the next pass, the entries holding for the run meanwhile. Put it in a folder that's writable and survives restarts (not a temporary folder, nor a container layer a new image replaces): a record lost is a withdrawal the service can replay past. lebroker's own book drops entries later ones hold over once it's full; this record keeps its own copy.
- **A read that fails decides nothing.** When the address book can't be read, the requests that need it wait for the next pass, neither signed nor declined, so the user's channels aren't told of a refusal the next pass may not make. The failure is logged once (`read-failed`, subject `address-book`) until a read succeeds. Everything else is signed as before.
- **What asks nothing of it.** Sends to Main's own address, to the gas reserve pinned for the deployment, and to a LaMarge escrow its SDK checks.
- **Not covered.** A LaMarge take paid inside Aster or Lighter pays a maker the service names, a counterparty no address book can name: it stays held to the take LaMarge's SDK checks, and what such a take pays stays unbounded by the allowlist, a known open item. LaMarge's PayTake isn't covered until lebroker #479 and this repository's #11 land: the allowlist's `payment` rule doesn't check a take's `receiveRecipient` or `amountOut` yet. Those PRs pin `receiveRecipient`, `receiveToken` and a floor on the total value delivered; once they land, PayTake is covered too. A withdrawal signed while the service is already compromised may never reach this signer, as the service may never list it: the record covers only the withdrawals it has seen.
- **Never signed here.** A request whose message carries an address-book entry, or its title anywhere, is refused before the allowlist runs (`This request asks Main to sign an address book entry: …`). Only the user approves a recipient, in their wallet.
- **The browser is unchanged.** It reads no address book: the wallet's prompt is the user's check there.
- **Rollout.** Until the user approves their sub-accounts, the transfers this signer signed on its own fall back to the browser. lebroker's web app prompts for the one signature that approves them all. Run this version against a lebroker that serves the address book in this form (lebroker PR #477): against an older one, every read fails, and transfers from Main to another account wait, neither signed nor declined.
- **Composing with LaMarge's send (lebroker's D69).** That rule takes its recipient through `ownSubAccount` too, so it inherits the check as soon as both are copied here.

## How it works

Per wallet:

1. **Sign-in, as the web app does.** `POST /api/v1/session/nonce`, then a Sign-In with Ethereum message naming the service's own host (`LEBROKER_URL`'s), the web's statement and a 5-minute expiry, signed with the wallet's key, then `POST /api/v1/session`. The message also names the resource `urn:lebroker:main-signer`: signed with the rest, it makes the session the signer's, and lebroker counts the signer as connected while that session's event stream is open. Meanwhile the web app asks nothing of the browser for the requests the signer signs, and the user's channels aren't asked for them either. The session lives in its cookie (`lebroker_session`, or `__Host-lebroker_session` over https). A call answered 401 signs in again once and is sent again. Changes carry the service's own `Origin`, as the browser's do. The session lebroker answers must name this wallet's own address, its user's and its own: every rule that names Main's own address reads it from there, so a session naming another is refused, and nothing is signed on it.
2. **Watching.** `GET /api/v1/events`, the event stream the web app subscribes to: each `signature-requests` event starts a pass. While the stream is down, a pass runs every 5 seconds; while it's up, every minute anyway. A dropped stream is opened again after 1 second, doubling up to 30.
3. **A pass.** `GET /api/v1/signature-requests`, then for the waiting ones `GET /api/v1/accounts` and `GET /api/v1/address-book`, each entry checked here and added to the record (above), the allowlist, the signature, and `POST /api/v1/signature-requests/<id>/sign` with `{ signature }`.
4. **Failures.** When the service or its venue fails (no answer, or 5xx), the signature is sent again on the next passes, 3 times in all. When the service refuses it (4xx: already settled, not Main's, refused by the venue), the signer stops there and logs why.

## Running it locally

With [Bun](https://bun.sh) 1.4 or later:

```sh
bun install
MAIN_KEYS_DIR=~/wts LEBROKER_URL=http://127.0.0.1:8190 bun run main-signer
```

Ctrl+C stops it.

| Variable                 | Default                                | What it is                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------ | -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `LEBROKER_URL`           | required                               | The lebroker service's address, such as `http://127.0.0.1:8190` for the local stack's executor. Plain `http` is refused unless the host is this machine (`localhost`, `127.x.x.x`, `::1`): the session cookie and Main's signatures cross the wire. Use `https` for any other host. Its origin also names the deployment the allowlist signs for, as the page's own does in the browser: a payment for gas goes only to the reserve pinned for it. |
| `MAIN_KEYS_DIR`          | required                               | A folder of key files, one per Main wallet, each named `<label>.key`, with its key inside: 32 bytes in hex, with or without `0x`. The file's name is the wallet's label in the logs. A leading `~` is the home folder.                                                                                                                                                                                                                             |
| `MAIN_WALLETS`           | all of the folder's                    | The wallets to run, by label, separated by commas: `main,sec`.                                                                                                                                                                                                                                                                                                                                                                                     |
| `MAIN_CHAIN_ID`          | none                                   | The chain your browser wallet usually shows. A venue setup asked from the browser names it, and Hyperliquid's rules accept it beside Arbitrum, as the browser does. Sign-in messages name it too (Ethereum's id otherwise).                                                                                                                                                                                                                        |
| `MAIN_ADDRESS_BOOK_FILE` | `address-book.json` in `MAIN_KEYS_DIR` | The file of the address-book entries this signer checked (above): messages and signatures, no key. A leading `~` is the home folder. Keep it: removed, the signer forgets the withdrawals it saw.                                                                                                                                                                                                                                                  |

The key folder follows the rules of lebroker's former `WALLET_KEYS_DIR`. Other files and hidden ones are left alone. The start stops on a malformed key, two files of one wallet, or a folder with no key file. It also stops on a key file its group or others can read (`chmod 600` it); that check is skipped on Windows, where a file's access list, not its permission bits, says who reads it. Errors name a file by its label, never by its key or its path. Unlike the executor, there's no cap on the number of wallets: the executor's cap came from venue connections, and this signer opens none.

Each wallet must be one that signs in to lebroker (a plain key, an EOA), and its user must be able to sign in there.

## Logs

One JSON line per event on standard output: `time`, `event`, the wallet's `wallet` (label) and `address`, and for a request its `requestId`, `kind` and `venue`.

| `event`              | Fields                                                                                                                     |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `started`, `stopped` |                                                                                                                            |
| `session`            | `stage`: `signed-in` or `renewed`                                                                                          |
| `session-failed`     | `error`                                                                                                                    |
| `stream`             | `stage`: `connected` or `dropped`                                                                                          |
| `read-failed`        | `subject` (`signature-requests`, `accounts`, `address-book`, `events`), `error`; `address-book` once until a read succeeds |
| `signed`             | `action`, decoded from what was signed, and `chainId`                                                                      |
| `refused`            | `reason`, the allowlist's                                                                                                  |
| `failed`             | `step` (`sign`, `send`, `decline`, or `record` for the address book's file), `error`, `status`, `attempt`, `retry`         |

A log line never holds a key, a signature or a request's payload. The keys stay in a private field (`WalletKey`) that no log, JSON or inspection shows.

- `src/helpers/formatDate/`: the design system's `formatDate`, in its English locale (`en-GB`), which the allowlist's summaries use.
- `src/helpers/formatUsd/`: the design system's `formatUsd` at its defaults (cents, a plain $ sign), in the same locale, for the payment for gas's summary.
- `src/signableRequest/testing/builders/`: what `@lebroker/venues/model`'s request builders build, for the copied tests, from the copied domains and types.

## Developing

```sh
bun run check      # ESLint, Prettier, typecheck, tests
bun run format     # fixes the formatting
```

The code follows lebroker's conventions (its CONTRIBUTING.md): one object parameter typed `…Props`, braces on every `if`, enums for known values and messages, each folder's types, enums and constants in their own files, no `!`. ESLint enforces them.

The tests need no network and no real key. They run the signer against a fake of lebroker's service (`src/testing/fakeApi`), which checks sign-ins and signatures as the service does, with keys generated for each test.
